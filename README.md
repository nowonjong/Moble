# 👩‍💻 프로젝트 내 역할

본 프로젝트는 **5인 팀 프로젝트**로 진행되었으며,
저는 **관리자 프로그램 및 관리자 TCP 서버 구현**을 담당했습니다.

관리자 프로그램은 단순한 매장 관리 UI가 아니라
키오스크와 모바일 앱의 요청을 처리하는 **중앙 서버 역할**을 수행합니다.

```text
          Mobile App
              │
              │ TCP/IP + JSON
              ▼
┌──────────────────────────────┐
│        Admin System          │
│                              │
│      TCP Server : 9000       │
│                              │
│  주문 / 회원 / 포인트 / 매출 │
│  메뉴 / 테이블 / 재고 관리   │
└──────────────▲───────────────┘
               │
               │ TCP/IP + JSON
               │
          Kiosk / User
```

이를 통해 각 프로그램에서 발생한 데이터를 관리자 프로그램에서
통합적으로 처리할 수 있도록 구현했습니다.

# ⚙️ 관리자 시스템 역할

관리자 프로그램은 크게 두 가지 역할을 담당합니다.

### 1. 매장 관리 프로그램

관리자가 매장의 현재 상황을 확인하고 주문과 데이터를 관리합니다.

```text
Admin UI
 │
 ├── 실시간 주문
 ├── 테이블 현황
 ├── 메뉴 관리
 ├── 과거 주문
 ├── 회원 관리
 ├── 재고 관리
 └── 매출 리포트
```

### 2. 중앙 TCP 서버

키오스크와 앱에서 전달되는 요청을 수신하여
각 요청에 맞는 비즈니스 로직을 처리합니다.

```text
App ──────┐
          │
          ▼
      TCP Server
       (Admin)
          ▲
          │
Kiosk ────┘
```

즉, 관리자 프로그램은 **UI + TCP Server + 주문 처리 로직 + 데이터 관리**를 함께 담당합니다.

# 🌐 TCP/IP 통신 구조

관리자 프로그램에서 TCP 서버를 실행하고
키오스크와 모바일 앱이 클라이언트로 접속합니다.

```text
Port     : 9000
Protocol : TCP/IP
Encoding : UTF-8
Format   : JSON
```

## Request 처리 과정

```text
Client
   │
   │ JSON Request
   ▼
TCP Server
   │
   ▼
데이터 수신
   │
   ▼
JSON Deserialize
   │
   ▼
Action 확인
   │
   ▼
Switch / Request Routing
   │
   ▼
기능별 처리 Method
   │
   ▼
CSV / 주문 / 회원 / 포인트 처리
   │
   ▼
JSON Serialize
   │
   ▼
Response
   │
   ▼
Client
```

여러 종류의 요청을 하나의 서버에서 처리하기 위해
JSON 데이터에 포함된 `Action` 값을 기준으로 요청을 분기했습니다.

예를 들어 다음과 같은 형태로 동작합니다.

```text
Action = GET_MENU
          ↓
      메뉴 조회 처리

Action = NEW_ORDER
          ↓
      신규 주문 처리

Action = PAYMENT_COMPLETE
          ↓
      결제 완료 처리
```

이 구조를 통해 클라이언트 종류와 관계없이
하나의 서버에서 여러 기능을 처리할 수 있도록 구성했습니다.

# 📨 주요 통신 Action

## 📱 App → Admin

| Action | 기능 |
|---|---|
| `REGISTER_MEMBER` | 신규 회원 등록 |
| `LOGIN_MEMBER` | 로그인 및 회원정보 확인 |
| `GET_MENU` | 최신 메뉴 정보 조회 |
| `NEW_APP_ORDER` | 앱 주문 등록 |
| `GET_ORDER_STATUS` | 주문 상태 조회 |

앱은 주문을 전송한 이후 `GET_ORDER_STATUS`를 이용하여
현재 주문 상태를 지속적으로 확인합니다.

---

## 🧾 Kiosk → Admin

| Action | 기능 |
|---|---|
| `GET_MENU` | 메뉴 정보 조회 |
| `GET_MEMBER` | 회원 및 포인트 조회 |
| `NEW_ORDER` | 신규 키오스크 주문 등록 |
| `PAYMENT_COMPLETE` | 결제 완료 처리 |

## 🖥 Admin 내부 주문 처리

관리자 UI에서는 앱 주문을 처리하기 위한 로직도 수행합니다.

```text
주문 수락
주문 거절
조리 완료
```

앱 주문의 상태를 관리자가 변경하면

# 🔄 주문 처리 흐름

키오스크와 앱은 **결제 시점과 주문 처리 방식이 다르기 때문에**
각각 별도의 처리 흐름을 구현했습니다.

---

## 🧾 키오스크 주문

```text
Kiosk
  │
  ▼
GET_MENU
  │
  ▼
메뉴 선택
  │
  ▼
GET_MEMBER
  │
  ▼
회원 / 포인트 확인
  │
  ▼
NEW_ORDER
  │
  ▼
실시간 주문 등록
  │
  ▼
조리
  │
  ▼
결제
  │
  ▼
PAYMENT_COMPLETE
  │
  ▼
금액 / 포인트 검증
  │
  ▼
ReceiptNo 생성
  │
  ▼
매출 저장
  │
  ▼
포인트 사용 / 적립
  │
  ▼
실시간 주문 제거
  │
  ▼
과거 주문 반영
```

### `NEW_ORDER`

키오스크에서 주문이 발생하면 관리자 서버가 주문 데이터를 받아
실시간 주문 데이터에 추가합니다.

매장 주문의 경우 테이블 번호를 이용하여
어느 테이블에서 발생한 주문인지 구분합니다.

---

## 💳 `PAYMENT_COMPLETE`

키오스크에서 실제 결제가 완료되면
`PAYMENT_COMPLETE` 요청이 관리자 서버로 전달됩니다.

```text
PAYMENT_COMPLETE
       │
       ▼
주문 데이터 확인
       │
       ▼
금액 / 포인트 검증
       │
       ▼
ReceiptNo 생성
       │
       ▼
Sales History 저장
       │
       ▼
회원 포인트 처리
       │
       ▼
Realtime 주문 삭제
       │
       ▼
Order Item Key 변경
       │
       ▼
주문 완료
```

주문 완료 시 주문 항목의 `KeyId`를
최종 `ReceiptNo` 기준으로 변경하여 완료 주문과 연결합니다.

매장 주문의 경우 결제가 완료되면
해당 테이블을 다시 빈 테이블 상태로 변경합니다.

## ❌ 앱 주문 거절

관리자가 접수 대기 상태의 주문을 거절할 경우
정상 완료 주문과 분리하여 처리합니다.

```text
접수 대기
   │
   ▼
주문 거절
   │
   ├── realtime 데이터 삭제
   ├── payment 임시 데이터 삭제
   ├── order item 데이터 삭제
   │
   ▼
rejection 기록
```

거절 주문은 매출 완료 데이터에 포함하지 않고
별도의 거절 기록으로 관리합니다.

---

## 📦 앱 픽업 완료

```text
   │
   ▼
매출 정보 생성
   │
   ▼
Sales History 저장
   │
   ▼
회원 포인트 처리
   │
   ▼
Realtime 주문 삭제
   │
   ▼
임시 Payment 데이터 정리
   │
   ▼
주문 완료
```

## 5. 회원 관리

![회원 관리](docs/images/admin-members.png)

회원정보와 포인트를 조회하고 관리할 수 있도록 구현했습니다.

### 주요 기능

- 전체 회원 조회
- 회원명 검색
- 연락처 검색
- 회원번호 확인
- 회원명 확인
- 연락처 확인
- 주소 확인
- 가입일 확인
- 현재 포인트 확인
- 회원정보 수정
- 회원 삭제

회원 데이터는 주문 및 결제 과정의
포인트 사용·적립 기능과 연동됩니다.

### 포인트 처리

```text
회원 조회
   │
   ▼
현재 포인트 확인
   │
   ▼
포인트 사용
   │
   ▼
결제 완료
   │
   ├── 사용 포인트 차감
   │
   └── 신규 포인트 적립
```

주문 완료 시 결제금액을 기준으로
포인트 적립 정보를 함께 처리하도록 구현했습니다.

# 💡 핵심 구현 포인트

## 1. 하나의 관리자 프로그램에서 여러 Client 처리

앱과 키오스크는 서로 다른 기능과 주문 흐름을 가지고 있지만
동일한 관리자 TCP 서버와 통신하도록 구현했습니다.

```text
             Admin TCP Server
              /           \
             /             \
          Kiosk             App
```

클라이언트별로 서버를 따로 구현하지 않고
`Action`을 기준으로 요청을 분기하여 처리했습니다.

---

## 2. 서로 다른 주문 흐름 통합

키오스크와 앱은 결제 시점이 다릅니다.

```text
[Kiosk]

주문
 ↓
조리
 ↓
결제
 ↓
완료


[App]

선결제
 ↓
접수 대기
 ↓
주문 수락
 ↓
조리
 ↓
픽업
 ↓
완료
```

따라서 주문 출처와 현재 상태를 기준으로
서로 다른 처리 로직을 적용했습니다.

---

## 3. 주문 상태 기반 데이터 관리

앱 주문을 단순히 저장하는 것이 아니라
현재 주문의 진행 상태를 관리하도록 구현했습니다.

```text
접수 대기
   ↓
주문 수락
   ↓
조리 중
   ↓
조리 완료
   ↓
픽업 완료
```

관리자에서 상태가 변경되면 앱은
`GET_ORDER_STATUS`를 통해 변경된 상태를 확인합니다.

---

## 4. 주문 완료 시 여러 데이터 동시 처리

하나의 주문이 완료되면 주문 상태만 변경되는 것이 아니라
여러 데이터를 함께 처리해야 했습니다.

```text
주문 완료
   │
   ├── 실시간 주문 정리
   ├── 주문 상세 연결
   ├── 결제 정보 처리
   ├── 회원 포인트 처리
   ├── 매출 저장
   └── 과거 주문 반영
```

이를 통해 주문, 회원, 포인트, 결제, 매출 데이터가
서로 연결되는 업무 흐름을 구현했습니다.

---

## 5. 실시간 데이터와 완료 데이터 분리

현재 진행 중인 주문과 이미 완료된 주문을
서로 다른 데이터로 관리했습니다.

```text
Realtime
   │
   │ 결제 / 픽업 완료
   ▼
Sales History
```

이를 통해 관리자 화면에서도
**실시간 주문 / 과거 주문 / 매출 리포트**를 각각 구분하여 관리할 수 있도록 했습니다.

# ⚠️ 한계 및 개선 방향

## 1. CSV → 관계형 데이터베이스

현재 프로젝트에서는 학습 및 프로젝트 규모를 고려하여
CSV 파일을 데이터 저장소로 사용했습니다.

실제 서비스 환경에서는 관계형 데이터베이스를 적용하여
다음 부분을 개선할 수 있습니다.

- 데이터 관계 관리
- 동시 접근 처리
- 트랜잭션
- 데이터 무결성
- 검색 성능
- 백업 및 복구

---

## 2. 재고 자동 차감

현재는 재고 현황과 재고 주문 기능을 구현했으며
메뉴 판매에 따른 재료 자동 차감은 구현하지 않았습니다.

향후 메뉴별 레시피 정보를 추가하면 다음과 같이 확장할 수 있습니다.

```text
주문 완료
   ↓
판매 메뉴 확인
   ↓
메뉴별 사용 재료 조회
   ↓
필요 수량 계산
   ↓
재고 자동 차감
   ↓
안전재고 확인
   ↓
부족 재고 알림
```

---

## 3. TCP 통신 안정성 강화

실제 서비스에서는 다음과 같은 네트워크 예외 상황을
추가적으로 고려할 필요가 있습니다.

- Client 비정상 종료
- Network Timeout
- 잘못된 JSON 요청
- 서버 재시작
- 중복 요청
- 주문 처리 도중 연결 종료

향후 요청 ID, 중복 요청 방지, 재시도 정책,
통신 로그 등을 추가하여 안정성을 높일 수 있습니다.

---

## 4. 보안 강화

현재 프로젝트는 교육 목적의 로컬 환경을 중심으로 구현했습니다.

실제 서비스 환경으로 확장한다면 다음과 같은 보완이 필요합니다.

- 회원 비밀번호 Hash 처리
- 민감한 개인정보 보호
- 통신 구간 암호화
- 관리자 인증 및 권한 관리
- 중요 데이터 접근 제어

# 📝 프로젝트 회고

이번 프로젝트를 통해 처음으로 **TCP/IP 통신을 직접 구현하고
여러 프로그램이 데이터를 주고받는 구조**를 경험했습니다.

단일 WinForms 프로그램을 구현할 때와 달리
앱과 키오스크가 서로 다른 시점에 요청을 보내기 때문에
각 프로그램이 동일하게 이해할 수 있는 **통신 규격과 데이터 구조를 설계하는 과정의 중요성**을 배웠습니다.

특히 키오스크 주문과 모바일 앱 주문은 결제 시점과 주문 진행 방식이 달라
하나의 관리자 프로그램에서 두 주문 방식을 모두 처리하기 위해
주문 출처와 상태를 기준으로 처리 로직을 구분했습니다.

또한 주문 하나가 완료될 때 주문 데이터뿐만 아니라
회원, 포인트, 결제, 매출 등 여러 데이터가 함께 변경되어야 했기 때문에
**기능 단위의 구현을 넘어 전체 데이터 흐름을 고려하는 경험**을 할 수 있었습니다.

팀원들과 앱·키오스크의 JSON 요청 형식과 통신 규격을 맞추고
실제 연동 과정에서 발생하는 문제를 해결하면서
**TCP/IP 통신과 프로그램 간 시스템 통합에 대한 이해를 높일 수 있었습니다.**
