# 📌 프로젝트 소개

초밥 매장의 실제 운영 흐름을 가정하여 **키오스크, 사용자 프로그램, 모바일 앱, 웨이팅 프로그램, 관리자 프로그램을 각각 구현하고 서로 연동한 통합 매장 관리 시스템**입니다.

단순한 주문 프로그램을 만드는 것이 아니라 주문 발생 이후의 처리 과정까지 연결하는 것을 목표로 개발했습니다.

```text
고객 주문
   ↓
주문 데이터 전송
   ↓
관리자 서버 주문 접수
   ↓
조리 상태 관리
   ↓
결제 / 픽업 완료
   ↓
회원 포인트 처리
   ↓
과거 주문 저장
   ↓
매출 집계
```

각 프로그램은 독립적으로 구현하되 **TCP/IP Socket과 JSON을 이용하여 데이터를 주고받도록 구성**했습니다.

관리자 프로그램은 앱과 키오스크의 요청을 처리하는 중앙 TCP 서버 역할과 동시에 매장 운영에 필요한 데이터를 관리하는 역할을 수행합니다.

# 🌐 TCP/IP 통신 구조

관리자 프로그램에서 **TCP Server**를 실행하고 앱과 키오스크가 Client로 접속하도록 구성했습니다.

### Server

```text
Port     : 9000
Encoding : UTF-8
Format   : JSON
Protocol : TCP/IP
```

### 요청 처리 구조

```text
Client
   │
   │ JSON Request
   ▼
TCP Server
   │
   ▼
데이터 수신
   │
   ▼
JSON Deserialize
   │
   ▼
Action 확인
   │
   ▼
기능별 처리 Method
   │
   ▼
주문 / 회원 / 포인트 / CSV 처리
   │
   ▼
JSON Serialize
   │
   ▼
SUCCESS / FAIL
   │
   ▼
Client
```

클라이언트가 보낸 JSON 데이터의 `Action` 값을 확인하여 해당 기능을 처리하는 메서드로 분기하도록 구성했습니다.

이를 통해 하나의 TCP 서버에서 여러 종류의 요청을 처리할 수 있도록 했습니다.

---

# 📨 주요 통신 Action

| Action | 요청 프로그램 | 기능 |
|---|---|---|
| `REGISTER_MEMBER` | App | 신규 회원 등록 |
| `LOGIN_MEMBER` | App | 로그인 및 회원정보 확인 |
| `GET_MEMBER` | Kiosk | 회원 및 포인트 조회 |
| `GET_MENU` | App / Kiosk | 최신 메뉴 정보 조회 |
| `NEW_ORDER` | Kiosk | 키오스크 주문 등록 |
| `NEW_APP_ORDER` | App | 앱 주문 등록 |
| `PAYMENT_COMPLETE` | Kiosk | 결제 완료 및 주문 마감 |
| `GET_ORDER_STATUS` | App | 앱 주문 상태 조회 |

관리자 프로그램 내부에서는 앱 주문을 관리하기 위한 주문 거절 및 픽업 완료 처리 로직도 수행합니다.

# 🔄 주문 처리 흐름

키오스크 주문과 모바일 앱 주문은 **결제 시점이 서로 다르기 때문에 각각 다른 처리 흐름**을 구성했습니다.

## 🧾 키오스크 주문

키오스크 주문은 먼저 실시간 주문으로 등록되고 실제 결제가 완료된 시점에 최종 마감됩니다.

```text
GET_MENU
   ↓
메뉴 선택
   ↓
GET_MEMBER
   ↓
회원 / 포인트 확인
   ↓
NEW_ORDER
   ↓
실시간 주문 등록
   ↓
조리 중
   ↓
결제
   ↓
PAYMENT_COMPLETE
   ↓
금액 / 포인트 검증
   ↓
ReceiptNo 발급
   ↓
매출 데이터 저장
   ↓
회원 포인트 처리
   ↓
실시간 주문 정리
   ↓
과거 주문 반영
```

### PAYMENT_COMPLETE

결제 완료 요청이 들어오면 다음 작업을 처리합니다.

```text
PAYMENT_COMPLETE
       │
       ▼
금액 / 포인트 검증
       │
       ▼
ReceiptNo 생성
       │
       ▼
매출 데이터 저장
       │
       ▼
포인트 사용 / 적립
       │
       ▼
realtime 데이터 정리
       │
       ▼
order_items KeyId
ReceiptNo로 변경
       │
       ▼
주문 완료
```

매장 주문의 경우 결제 완료 후 사용 중이던 테이블도 다시 빈 테이블 상태로 변경합니다.

선결제
   ↓

   ↓
접수 대기
   ↓

   ↓
조리 중
   ↓
조리 완료

   ↓

## ❌ 앱 주문 거절

관리자가 접수 대기 중인 앱 주문을 거절할 수도 있습니다.

```text
접수 대기
   ↓
주문 거절
   ↓
realtime 데이터 정리
   ↓
item 데이터 정리
   ↓
payment 임시 데이터 정리
   ↓
rejection 기록
```

거절된 주문은 정상 완료 주문 및 매출 데이터와 분리하여 관리합니다.

# 💾 CSV 데이터 관리

프로젝트에서는 주문, 회원, 메뉴, 결제 및 매출 데이터를 **CSV 파일 기반으로 저장하고 관리**했습니다.

데이터의 목적과 주문 처리 단계에 따라 파일을 분리했습니다.

| CSV File | 역할 |
|---|---|
| `susi_orders_realtime.csv` | 현재 처리 중인 주문 |
| `susi_order_items.csv` | 주문별 메뉴 상세 |
| `susi_order_payments.csv` | 결제 및 포인트 관련 임시 정보 |
| `susi_sales_history.csv` | 완료 주문 및 매출 이력 |
| `susi_order_rejections.csv` | 거절된 앱 주문 |
| `susi_menu.csv` | 메뉴 정보 및 판매 상태 |
| `member.csv` | 회원 정보 및 포인트 |

### 주문 데이터 처리 구조

```text
                    주문 발생
                        │
                        ▼
             실시간 주문 데이터
       susi_orders_realtime.csv
                        │
              ┌─────────┴─────────┐
              │                   │
           정상 처리            주문 거절
              │                   │
              ▼                   ▼
       결제 / 픽업 완료       rejection 기록
              │
              ▼
         매출 데이터 생성
              │
              ▼
       susi_sales_history.csv
              │
              ▼
           매출 리포트
```

실시간 주문과 완료된 주문을 분리함으로써 **현재 처리 중인 주문과 마감된 주문 데이터를 구분**했습니다.

```text
고객 웨이팅 등록
       ↓
중복 여부 확인
       ↓
대기열 등록
       ↓
테이블 상태 확인
       ↓
빈 테이블 발생
       ↓
대기열 이동
       ↓
순번 변경
       ↓
SMS 알림
```

키오스크와 웨이팅 프로그램은 테이블 상태 정보를 공유합니다.

```text
Kiosk
   │
   ▼
table_state.json
   ▲
   │
Waiting
```

### 테이블 상태

```text
착석
 → OCCUPIED

결제 완료
 → AVAILABLE
 → ReleaseSequence + 1
```

웨이팅 프로그램에서는 테이블 상태를 확인하여 해제된 테이블 수만큼 대기열을 이동시키고 입장 및 순번 변경 SMS를 발송합니다.

# 💡 핵심 구현 경험

## 1. TCP/IP 기반 Client-Server 구조

기존의 단일 WinForms 프로그램에서 벗어나 서로 다른 프로그램이 네트워크를 통해 데이터를 주고받는 구조를 구현했습니다.

```text
App ──────┐
          │
          ▼
      TCP Server
       (Admin)
          ▲
          │
Kiosk ────┘
```

이를 통해 UI 구현뿐 아니라 **Socket 통신, JSON 데이터 교환, 요청 분기, 주문 상태 관리**를 함께 경험했습니다.

---

## 2. Action 기반 Request Routing

여러 종류의 클라이언트 요청을 하나의 서버에서 처리하기 위해 JSON의 `Action` 값을 기준으로 기능을 구분했습니다.

```text
JSON Request
     ↓
Deserialize
     ↓
Action 확인
     ↓
기능별 분기
     ↓
Business Logic
     ↓
JSON Response
```

회원, 메뉴, 주문, 결제 등의 요청을 동일한 TCP 서버에서 처리할 수 있도록 구성했습니다.

---

## 3. 서로 다른 주문 방식 통합

키오스크와 모바일 앱은 주문 및 결제 흐름이 서로 다릅니다.

```text
[Kiosk]

주문
 ↓
조리
 ↓
결제
 ↓
주문 완료


[App]

선결제
 ↓
접수 대기
 ↓
관리자 수락
 ↓
조리
 ↓
픽업
 ↓
주문 완료
```

두 주문 방식을 하나의 관리자 시스템에서 처리하기 위해 주문 출처와 상태에 따라 처리 로직을 구분했습니다.

---

## 4. 주문 상태 관리

특히 앱 주문은 여러 단계의 상태를 가지도록 구현했습니다.

```text
접수 대기
   ↓
주문 수락
   ↓
조리 중
   ↓
조리 완료
   ↓
픽업 완료
```

정상 흐름뿐만 아니라 주문 거절과 같은 예외 흐름도 별도로 처리했습니다.

---

## 5. 주문·회원·포인트·매출 연계

주문 하나가 완료될 때 여러 종류의 데이터를 함께 처리하도록 구현했습니다.

```text
주문
 ↓
주문 상세
 ↓
결제
 ↓
회원 확인
 ↓
포인트 사용 / 적립
 ↓
매출
 ↓
과거 주문
```

이를 통해 각 기능이 독립적으로 동작하는 것이 아니라 **하나의 업무 흐름 안에서 데이터가 서로 연결되는 구조**를 경험했습니다.

---

## 6. 실시간 데이터와 완료 데이터 분리

처리 중인 주문과 완료된 주문을 별도로 관리했습니다.

```text
실시간 주문
    ↓
결제 / 픽업 완료
    ↓
실시간 데이터 정리
    ↓
완료 주문 / 매출 데이터 생성
```

이 구조를 통해 관리자는 현재 처리해야 하는 주문과 이미 완료된 주문을 각각 다른 화면에서 관리할 수 있습니다.

# ⚠️ 한계 및 개선 방향

## 1. 재고 자동 차감

현재 재고 시스템은 **재고 현황 확인 및 재고 주문 기능까지 구현**되어 있습니다.

판매 메뉴와 재료의 연결 정보가 추가된다면 향후 다음과 같이 확장할 수 있습니다.

```text
주문 완료
   ↓
판매 메뉴 확인
   ↓
메뉴별 필요 재료 확인
   ↓
재료 사용량 계산
   ↓
현재 재고 자동 차감
   ↓
안전재고 확인
   ↓
재고 부족 알림
```

---

## 2. 메뉴 이미지 중앙 관리

현재 프로젝트는 로컬 실행 환경을 중심으로 구현했습니다.

실제 서비스 환경에서는 메뉴 이미지를 공용 서버 또는 Cloud Storage에 저장하고 각 프로그램이 동일한 이미지를 조회하도록 개선할 수 있습니다.

```text
관리자 메뉴 등록
       ↓
Image Server / Cloud
       ↓
Image URL 저장
       ↓
App / Kiosk
       ↓
이미지 조회
```

---

## 3. CSV 기반 데이터 저장

프로젝트 규모와 학습 목적을 고려하여 CSV 파일 기반으로 데이터를 관리했습니다.

실제 운영 환경으로 확장할 경우 관계형 데이터베이스를 적용하여 다음과 같은 부분을 개선할 수 있습니다.

- 주문·회원·결제·매출 간 관계 관리
- 동시 접근 처리
- 트랜잭션을 통한 데이터 일관성 확보
- 검색 성능 개선
- 데이터 무결성 관리
- 백업 및 복구

---

## 4. 네트워크 예외 처리 강화

실제 서비스 환경에서는 단순 요청·응답뿐 아니라 다음과 같은 상황에 대한 추가적인 처리가 필요합니다.

```text
Client 연결 종료
Network Timeout
잘못된 JSON 요청
Server 재시작
중복 주문 요청
결제 완료 중 연결 종료
```

향후에는 요청 ID, 재시도 정책, 로그 시스템 등을 추가하여 통신 안정성을 높일 수 있습니다.

# 📝 프로젝트 회고

이번 프로젝트를 통해 처음으로 **TCP/IP 통신을 직접 구현하고 서로 다른 프로그램이 데이터를 주고받으며 하나의 시스템으로 동작하는 과정**을 경험했습니다.

처음에는 각각의 화면을 구현하는 것보다 프로그램 간 **통신 규격과 데이터 처리 흐름을 일치시키는 과정**이 더 어렵다는 것을 경험했습니다.

특히 키오스크와 모바일 앱은 주문 및 결제 시점이 서로 달랐기 때문에 각 클라이언트의 요청을 하나의 관리자 시스템에서 처리할 수 있도록 주문 상태와 데이터 처리 시점을 구분해야 했습니다.

또한 주문 하나가 완료되는 과정에서 주문 정보뿐 아니라 회원, 포인트, 결제, 매출 등의 데이터가 함께 변경되기 때문에 **여러 데이터가 서로 연결되는 업무 흐름을 고려하여 프로그램을 설계하는 경험**을 할 수 있었습니다.

팀원들과 JSON 요청·응답 형식과 통신 규격을 맞추고 연동 과정에서 발생한 문제를 해결하면서 **TCP/IP 통신과 시스템 통합에 대한 이해를 높일 수 있었습니다.**
